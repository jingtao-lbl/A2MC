Getting started with A2MC

From a machine with nothing installed to a calibration case ready for its first round.

Steps

  1. Install Claude Code
  2. Sign in
  3. Clone A2MC
  4. Python environment
  5. Activate A2MC
  6. Wire up A2MC
  7. Build and verify your model
  8. Create your case
  9. Run the first round
  10. Every session after
  11. Summary

What you will have at the end

  • A working A2MC clone, wired so its own checks run, with an agent that knows who you are.
  • Your model built on your machine, archived, and checked against the version A2MC’s knowledge base describes.
  • A calibration case of your own, ready for its first round: a research plan you approved, targets from your data, and a parameter list with a source for every bound.

The short version

Do steps 1 and 2 yourself. The terminal session you open to sign in can do steps 3 and 4 for you with claude.

Then open a new terminal, go into your A2MC clone and start Claude there (step 5). That is the moment the A2MC agent activates, with its skills and project instructions loaded. Ask it to help you set up A2MC.

From there it works with you through steps 6 to 9, and stops where the decision is yours: your compute account, what your data can constrain, and the research plan. Building your model (step 7) is the one part that is a real, sometimes slow, build on your own machine.

Steps 1–6 take about twenty minutes. Step 7 depends on your model: EcoSIM builds in about half an hour. Steps 8 and 9 are the science, and take as long as your questions deserve.

Install Claude Code

Once per machine · needs Node.js 18 or newer

Install Claude Code by running the command in your terminal:

If npm is missing, install Node.js first from nodejs.org. On a shared cluster you may need module load nodejs (or your site's equivalent) instead.

Claude Code is the harness the A2MC agent runs in. A2MC itself is harness-neutral: its operating contract is AGENTS.md and its capabilities are the skills under .claude/skills/, so another coding agent can follow them too. But since A2MC's start-up and hooks are written for Claude Code, it is better using Claude to run A2MC right now.

02

Sign in, either way

Once per machine

Start this first session in your home directory, so it can see the place your clone will go. Claude Code accepts a Claude subscription or an API key. Either works for everything in this guide; the subscription is usually simpler and has no per-token billing to watch.

Two agents, and they sign in separately

Everything in this guide is the offline agent: you, talking to Claude Code in the repo. It uses the sign-in above and nothing else.

The variables you will see in A2MC's own config (A2MC_AI_PROVIDER, A2MC_AI_API_KEY_ENV) belong to the online agent, the unattended orchestrator.py --run loop. You do not need them to follow this page, and you do not need an API key at all if you use a subscription.

Once you are signed in you can already ask Claude in this session to do steps 3 and 4 for you. It needs this page, the tutorial file you are reading, somewhere it can read it: a session can only read files on the machine it runs on, so if you signed in on a remote cluster, copy the file there first (for example with scp). Then enter the prompt with that file's path:

PromptHelp me setup A2MC following steps 3 and 4 of this tutorial: /path/to/A2MC_Getting_Started.html

04

Python environment

Once per machine

A2MC's config expects a virtual environment at ~/a2mc_env, at exactly that path, because that is where the machine config looks for it. Build it from Python 3.10 or 3.11: requirements.txt notes that the RAG store (chromadb) needs 3.10, and the Perlmutter environment A2MC is developed in is 3.11. That is not necessarily what python3 is on your machine. On Perlmutter, and on many clusters, python3 is the operating system's Python 3.6, and an environment built from it cannot run A2MC. So check first:

Then build the environment with that Python, and install the requirements from inside the clone: requirements.txt sits at the repo root, and a fresh terminal does not start there.

On Perlmutter a Python module is another source: module load python/3.11-24.1.0, then python -m venv ~/a2mc_env. On a Mac, a Homebrew Python 3.12 refuses pip install outright (PEP 668). If the install fails on your machine, hand it to the agent rather than debugging it alone. That is what step 5 is for.

05

Activate A2MC

Every session

Close the above terminal session you opened in step 2, open a new terminal, cd into your A2MC clone, and start Claude there. It loads A2MC's project instructions (CLAUDE.md, AGENTS.md), its skills, and its hooks from that folder, and that is the moment the A2MC agent activates.

A2MC's start-up hook then takes a snapshot of the clone and gives it to the agent. You will not see the snapshot on screen: Claude Code hands a start-up hook's output to the agent, not to you. So the snapshot tells the agent to report, in its first reply, anything you need to know: an unfinished clone or setup, disk space running low, or a calibration whose saved state cannot be resumed. On a fresh clone it is usually these two:

The agent tells youWhat it means
the clone is not fully set upper-clone settings that git cannot carry are missing; step 6 fixes them
setup is at stage N, and the next step is a named skillwhere you are in setup, read from disk rather than from memory

You can find out where you are in setup by asking the agent, and the agent will pick up and finish the whole initialization and onboarding set up steps for you, against a checklist required by the setup-discipline skill. The agent checks the setup status by running A2MC's setup router, which reads your setup state from disk rather than from memory. Wire up the A2MC clone

Once per clone · skill: a2mc-init Steps 0 and 1

Ask the agent to set up the A2MC clone:

Tell the agentHelp me set up A2MC. Follow the setup tutorial in docs/tutorial/A2MC_Getting_Started.html.

From here the agent leads. It runs the a2mc-init skill, the front door for a new clone, and interviews you: a few short questions at a time. The first time you ask, it opens with exactly this:

The agent asksHi! I'm your A2MC agent, and I'll work with you as your science assistant to calibrate your model. What's your name, and how should I address you?

This first interview is about you and your setup, not yet your science:

The agent asksWhy
your name, and how to address youit goes on every log A2MC writes for you. Declining is fine: the logs then say A2MC user

whether you will run on a cluster with a scheduler or on a workstationa workstation runs the ensemble itself, with no scheduler, and the agent watches it with the arm-local-monitoring skill; a cluster runs it through the scheduler, watched with arm-hpc-monitoring. The questions about your science (your goal, your data, your site, your targets) come in step 8, in a second interview. The questions about where things live on your machine come in steps 7 and 8. So you never have to guess in advance what to tell it.

Once it knows who you are, it wires the clone. A few settings live outside the files git tracks, so every fresh clone starts without them. The most important is core.hooksPath, which switches on the repository's own commit checks. It is stored per clone and git cannot carry it, so a fresh clone starts with those checks off, and a commit that runs no checks looks exactly like a commit that passes them. This is the one setting worth knowing by name: if A2MC ever stops refusing a malformed log or a badly formed commit message, git config core.hooksPath is the first thing to look at. setup_clone.sh sets it, and it is safe to run again at any time.

The second one explains a permanently dirty repository. A2MC ships its RAG indexes as tracked chroma.sqlite3 files, and ChromaDB rewrites them every time it reads one. So after your first RAG query, git status shows several files as modified and keeps showing them, forever, however many times you discard the changes. .gitignore cannot help: the files are tracked. The fix is git update-index --skip-worktree, which tells your clone to ignore local changes to exactly those files, and setup_clone.sh applies it. Re-run it if you ever add a RAG profile, since the flag is set per file. The one time to undo it is if you rebuild an index and want to commit the result: git update-index --no-skip-worktree first, or git will quietly ignore your rebuild.

Git needs to know who you are, too. Before your first commit, git refuses with “Please tell me who you are” unless it has a name and an email for you. If git config user.name prints nothing, set both, once per machine. They stay on your machine, and no account is involved:

This is separate from the name A2MC puts on its logs, which whoami.py records above. A commit is a save point in a history kept on your own machine: nothing leaves it unless you separately ask to push, which you never have to do.

07

Get your model built and verified on this machine

Once per model per machine · skill: a2mc-init Steps 2, 2b and 3

A2MC calibrates a model it can run. So before any case exists, the agent makes sure there is a built copy of your model on your machine, that it is safely archived, and that it matches what A2MC's knowledge base describes.

Where things go. A2MC hardcodes no paths, so the agent asks you where each of these lives on your machine and records every answer in a config variable. Decide them before you start: a shared cluster usually has a project or software space for sources and binaries, and a scratch or project space for output, which can grow large. Disk space is not yours to police: the agent keeps these locations off a node's temporary space and off a nearly full home directory, a hook stops it writing into a system temp directory, and where the machine reports quotas (NERSC does) A2MC's start-up check warns you in every session whose home or scratch space is running low.

The agent asksWhenRecorded in
where your model's source checkout is, or, if you have none, where to clone and build itthis step (a2mc-init Step 2)A2MC_MODEL_PATH
where archived copies of the built binary should livethis stepthe archive root; your case's binary variable points into it: A2MC_ECOSIM_BINARY, A2MC_PFLOTRAN_BINARY or A2MC_ATS_EXE
where this case's simulation output goesstep 8, in its interview (onboard-case Step 1, round 1A)A2MC_OUTPUT_ROOT (ATS: A2MC_CASE_ROOT)

ELM / ELM-FATES only: HPC project, E3SM checkout, output root, CIME case-scripts folder, emailthis step (a2mc-init Step 3)A2MC_PROJECT, A2MC_E3SM_ROOT, A2MC_OUTPUT_ROOT, A2MC_SCRIPTS_DIR, A2MC_EMAIL in a2mc_config.sh

For EcoSIM, PFLOTRAN and ATS every one of these belongs to the case, so it is written into the case's site config, and only after you approve the research plan (step 8, Gate 1). Two cases can use different checkouts or output places. For ELM and ELM-FATES they are machine-wide, in a2mc_config.sh.

If your model is new to A2MC, you skip this step's build and check, because onboard-model does that work with you instead. It asks the same first two questions before it builds anything (the source checkout, or where to clone it, and where archived binaries go). It also asks for a folder to run your model's own sample case in and, on a cluster, the account that run is charged to (its Step 0a). Once the model is registered, it checks your checkout against that registration, the same check this step runs for a known model. Step 8's questions are then the same for everyone.

Build it, if you have not. Each model has one build guide, and the agent follows it with you:

Archive the binary before any case uses it

A model builds into one shared directory, and the next build overwrites the executable in place. A queued job looks up its executable when it starts, not when it was submitted, so rebuilding while an ensemble waits in the queue silently changes what it runs. Right after a successful build, the agent archives a copy, and every case points at the archived copy, never at build/:

tools/model_archive_build.sh --tree <checkout> --binary <built executable> --archive <archive root>

Verify it. The agent checks your checkout against the model versions A2MC's knowledge base was built from:

VerdictWhat it means for you
matchyour commit is the one A2MC's knowledge base describes
DRIFTthe model is supported, and you are at a different commit. This is normal, and you proceed. The agent reasons with the registered description and notes the difference in your plan; it rebuilds that description only if your source differs in the mechanisms you calibrate
NO MILESTONEthe model's own onboarding is unfinished; the agent resumes it with onboard-model
CANNOT VERIFYno version could be read: a wrong path, or a model installed without its git history

Fork-safe remotes (optional). If you will ever edit the model's source, the agent offers to point pushes at your own fork and disable pushes to the upstream project, and it verifies both directions. If you will only calibrate, you can decline; nothing depends on it.

The machine config. A2MC hardcodes no paths. Settings live in two layers, and which machine file you have depends on how your model is built:

FileHolds
a2mc_noncime_config.sh (EcoSIM, PFLOTRAN, ATS)only what every model shares: the Python environment, the AI provider, the default MPI layout. It deliberately holds no model path, binary or account: those belong to each case
a2mc_config.sh (ELM, ELM-FATES)the HPC project, the E3SM checkout, the output root, plus the shared settings. Check every value it ships with: it carries the developer's own paths
use_cases/<Model>_<Case>/config/<model>_<case>_config.sheverything true of this case on your machine. It loads the right machine config itself, and repairs the wrong one if it was loaded by mistake

When the agent finishes this step it runs the router again and tells you what is next, which for a model A2MC has is step 8.

08

Create your case, starting from your science question

Once per case, and again for every new case · skill: onboard-case

A case is one site, project or scenario. You can have many, each in its own folder under use_cases/. The agent builds it with you in this order, and it stops at two gates where the decision is yours:

  1. The interview. The agent leads again, and starts from your science rather than the model's internals. It first asks whether you already know your configuration (then it goes straight to the details) or would rather start from your question. Then, in short rounds:
    • what you are calibrating, and at what level: the whole ecosystem, or each plant type or region;
    • what data you have, and which of it calibrates the model versus validates it afterwards;
    • where the case runs: which model build, scheduler or workstation, which HPC account, and where output goes;
    • the model's configuration, and how it is spun up;
    • the site;
    • the targets, and how they combine into one score (most people take the defaults).
    Your data decides the targets, and whether you need detail per plant type at all. The agent never asks what it can read from your files.
  2. Bind the case to the model you built. The agent binds your answers from the interview: which checkout and archived binary the case runs, where its output goes and which account pays for it (the table in step 7). It repeats the version check for this case.
  3. Scaffold the case from your model's template: python tools/create_use_case.py --model <model> --case <Case>. Never copy a folder by hand: the tool renames the site config the rest of setup expects.
  4. The research plan (★ GATE 1). A plain-language plan of goal, targets, cost function, model configuration and parameter approach, written into the case for you to approve. Nothing, including the locations you gave in step 7, is written into the case's config until you do.
  5. The parameter list (★ GATE 2). Built from the mechanisms that drive your targets, each bound with its source recorded (measured, literature with a DOI, a database, or marked provisional). The agent never invents a bound.
  6. The readiness check. One command says whether the case is ready for its first round.
Why the source and the check are joined with &&

Typed by you, a sourced config stays in your terminal. Run by the agent, it is gone the moment the command ends, because each command the agent runs gets a fresh shell. Split across two commands, the check reports its settings unset as if nothing had been sourced. Joining them avoids that.

A ! in the check's output, such as model drift, is a warning and does not block. A ✗ does, and the agent fixes it with you.

One design decision cannot be taken back later

A round can draw an independent validation set: a second sample of parameter points drawn with a different seed, run like any other case, and held back. It is the only honest test of whether anything fitted to the round (a surrogate, an emulator) actually predicts, rather than reproduces the points it was fitted on. It must be drawn at design time, because no rearrangement of a finished ensemble makes an independent test of itself. It costs roughly 25% more simulations. The settings are A2MC_SOBOL_SEQ_VALID_SAMPLES, A2MC_SOBOL_SEQ_VALID_SEED and A2MC_VALID_MATRIX_FILE, and the agent will ask.

Once the readiness check passes

The agent uses phase0-design to sample the parameter space and submit the ensemble, pausing before it submits thousands of jobs. If you would rather it drive the whole calibration loop and pause only where a decision is yours, ask for that instead; the skill is calibration-goal.

10

Every session after the first

Every session · skill: onboard-session

Open Claude in your clone as in step 5 and say:

Tell the agentCatch me up. Where did the last round leave off, and what is next?

The agent first checks that setup is really finished. If the clone is not wired, or a case never reached its first round, it routes you there instead of pretending to resume. Then it reads the most recent logs and the case's workflow state, checks for jobs in flight, and drives the next action, pausing only for a genuine decision: a gate, a knowledge-base write, an expensive or irreversible step. Before a session's first submission it re-runs the readiness check, which catches a model that was rebuilt, or a case folder that arrived from someone else still pointing at their machine.

▶

Summary of the setup playbook

Reference · the agent follows this; you can read it to see where you are

Setup is five skills, each owning one kind of thing, and a router that reads from disk which one applies. Agent: before anything else, run the router, then follow the path that matches the user's situation, and take each skill's steps in order. Every hand-off goes forward; a skill never promises the user they will "come back" to an earlier one.

SkillOwnsRuns
a2mc-initthe clone (name, wiring, GitHub question) and the model install on this machine (build, archive, verify), plus the machine configonce per clone; Step 2 once per model
onboard-modela model A2MC does not have: adapter, knowledge chain, milestone, build guide, case templateonce per new model
onboard-caseone case: interview, binding to the install, scaffold, plan, parameter list, readiness checkonce per case
onboard-sessionresuming a case that has reached its first roundevery session
setup-disciplinethe definition of done for each of the above, with the gate for each itemat the start and end of each stage

Path A: a new user, with a model A2MC has (EcoSIM, PFLOTRAN, ATS, ELM-FATES).

  1. a2mc-init Step 0: greet; record the name with whoami.py --set; gauge experience; which model; cluster or workstation. Tell a CIME user about A2MC-elm, and a workstation user that only EcoSIM runs locally today.
  2. a2mc-init Step 1: scripts/setup_clone.sh, then check_clone_setup.py must exit 0; ask the GitHub question.
  3. a2mc-init Step 2: ask where the model source is, or where to clone and build it, and where archived binaries go (step 7's table); build from models/<m>/BUILD.md if nothing is built (in the background: builds outlast a tool call), archive the binary, then model_preflight.py: match or DRIFT proceed, NO MILESTONE goes to onboard-model.
  4. a2mc-init Step 2b: offer fork-safe remotes; accept a decline.
  5. a2mc-init Step 3: the machine config for the model's family.
  6. a2mc-init Step 4: run the router, name the model's runbook skill, hand off to onboard-case.
  7. onboard-case Steps 1–6: interview → bind + verify this case's install, asking where its output goes and which HPC account runs it → scaffold → research plan (★ GATE 1) → parameter list (★ GATE 2) and round record → check_setup_ready.py exits 0 → phase0-design or calibration-goal.

Path B: a model A2MC has never seen. a2mc-init Steps 0, 1 and 3 (the wiring and the machine config do not depend on the adapter) → onboard-model Steps 0–14: first where things go (Step 0a: the source checkout or where to clone it, the archive root, a folder for the orientation run, and on a cluster the account), then the orientation run (Step 0d) that builds the model with the user and records the recipe in models/<m>/BUILD.md, and after the milestone is registered, model_preflight against that checkout, which must report a match → onboard-case, whose round 1A starts from those locations and whose Step 2 binds the case to that build.

Path C: a returning user, a new case. onboard-case directly. Its prerequisite checks confirm the clone is wired and the model onboarded; its Step 2 binds the new case to an install, which may be the same as the first case's.

Path D: a user who received a finished case folder. a2mc-init Steps 0 and 1 (a case folder never carries the clone's wiring), and Step 2 if the model is not built on this machine → onboard-session, whose Step 0 walks the site config's paths with the user, re-binds the case through onboard-case Step 2 (a re-bind, not a new case), runs the readiness check, and keeps the case out of the user's own fork with .git/info/exclude.

Path E: a setup left half-finished. the router names the owner, and the owner resumes at the first failing row: check_stage_ready.py --case <Case> for a case, --model <m> for a model. Never restart a stage.

Path F: every later session. onboard-session. It routes an unfinished setup first, then resumes and drives the next action the resolver gives.

GateAsksNeeds
python3 tools/check_clone_setup.pyis this clone wired?nothing sourced
python3 tools/check_stage_ready.pywhich setup stage, what is outstanding, what is next?nothing sourced
python tools/model_preflight.py --model <m> --checkout <path>does this checkout match what A2MC knows?the A2MC environment

Which Python: the command says. Commands written python3, such as the first two here and whoami.py, run under any Python 3, including a system Python as old as 3.6, because they run before anything is set up. Commands written python need the A2MC environment from step 4: in a shell that has sourced a config it is already active, and in a one-off shell, which is what each command the agent runs is, call ~/a2mc_env/bin/python instead.
